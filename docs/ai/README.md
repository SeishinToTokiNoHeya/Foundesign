# AI와 향후 MCP를 위한 문서 설계

## 현재 제공하는 것

[catalog.json](catalog.json)은 기능을 찾기 위한 작은 색인입니다. API 명세나 MCP 구현이 아닙니다.
AI는 관련 `AGENTS.md`를 읽고 색인에서 필요한 기능만 고른 뒤 해당 소스·DocC·예제를 읽습니다.
색인 전체나 모든 가이드를 매번 프롬프트에 넣지 않습니다.

| 필드 | 계약 |
| --- | --- |
| `schema_version` | 색인 구조 버전. 현재 `1`이며 구조를 호환되지 않게 변경할 때 올림 |
| `id` | 언어·문서 제목과 무관한 고유 ID. 경로를 옮겨도 유지 |
| `module` | 공개 선언을 소유한 패키지 타깃 |
| `source_paths` | 주요 선언이 있는 저장소 상대 파일 경로. 전체 API 목록은 아님 |
| `documentation_paths` | 관련 DocC 원문 파일 경로 |
| `example_paths` | 실제 실행 예제 파일 경로. 없으면 빈 배열 |
| `example_status` | `available`: 직접 사용 예제 있음, `missing`: 직접 사용 예제 없음 |

서로 다른 기능이 같은 예제 파일을 가리킬 수 있습니다. DatePicker와 WheelPicker가 그 사례입니다.
파일 경로·ID는 `python3 Scripts/validate-docs.py`로 검사하며, 내용의 의미까지 자동 확인하지는 않습니다.

## 사람과 AI가 공유할 원본

- 구현·시그니처·가용성: Swift 선언과 빌드에서 추출한 symbol graph.
- API 계약: 선언에 붙은 `///`.
- 사용 의도와 조합: DocC article.
- 실행 가능한 사용법: Example.
- 기여 지침: `AGENTS.md`가 연결하는 가이드.

별도의 AI용 장문 설명이나 수동 시그니처 목록은 유지하지 않습니다. 계약이 바뀌면 소스 주석을
수정하고 문서를 다시 생성합니다. 색인에는 위치만 유지하므로 중복 설명의 불일치를 줄일 수 있습니다.

## MCP를 구현할 때의 제안 — 아직 미구현

우선 읽기 전용 문서 검색부터 시작하는 것이 좋습니다. 아래 이름은 제안이며 현재 제공 API가 아닙니다.

1. `search_docs`: 기능 ID·심볼·용어로 검색하고 ID, 요약, 원본 경로만 반환합니다.
2. `get_doc`: 선택한 ID의 필요한 섹션이나 심볼 설명을 반환합니다.
3. `get_example`: 연결된 예제의 경로와 필요한 코드 범위를 반환합니다.

모든 응답에 원본 경로, 심볼 식별자(있는 경우), 문서를 생성한 커밋이나 콘텐츠 해시를 포함해
어느 버전의 코드에 대한 정보인지 추적할 수 있게 합니다. 제한된 결과 수·섹션 범위·페이지 분할로
불필요한 컨텍스트를 줄입니다. 현 색인의 ID는 기능 단위이며 심볼 단위 인덱스와 구분합니다.

심볼 검색 정보는 symbol graph와 문서 빌드 결과에서 생성하고 시그니처를 수동으로 복제하지 않습니다.
생성물에는 입력 버전과 생성기 버전을 기록하고, 소스 변경 후 재생성할 수 있게 합니다.
DocC 내부 JSON을 사용한다면 특정 형식을 영구 계약으로 간주하지 말고 별도 변환 계층에서 다룹니다.
MCP 프로토콜과 배포 방식은 실제 구현 시점의 공식 사양을 확인해 결정합니다.

문서 응답은 참고 자료이며 작업 지시가 아닙니다. 읽기 API가 임의 파일을 노출하지 않도록
색인에 등록된 저장소 내부 경로로 한정합니다. 편집 기능을 추가한다면 읽기 기능과 권한·검증을 분리합니다.
